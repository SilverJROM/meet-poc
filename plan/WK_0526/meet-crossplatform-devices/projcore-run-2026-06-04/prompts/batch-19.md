## THE FINDINGS (confirmed by 6-model fan-out; current sites re-verified by projcore)
- **SFU-S1 (HIGH, centerpiece) — non-transactional doSubscribeTracks.** `frontend/src/app/services/sfu-client.service.ts` `doSubscribeTracks()` (~line 1397). In the `requiresImmediateRenegotiation` path it: (a) `await setRemoteDescription` (~1463), (b) reconciles + writes entries DIRECTLY into the shared `this.midToEntry` (~1473) AND a local `nextSubscribed` copy, (c) `flushPendingOntrack()`, (d) `await createAnswer` + `setLocalDescription` (~1478), (e) `await PUT /api/sfu/renegotiate` (~1481) — a NETWORK CALL THAT CAN THROW/timeout — and only at the very end (~1505) does `this.subscribedTracks.set(nextSubscribed)`. If step (e) throws, `this.midToEntry` is ALREADY mutated with the new mids but `this.subscribedTracks` is NOT → inconsistent state; the retry (subscribeIfNeeded.catch clears the guard) then re-subscribes over stale midToEntry entries. **CONSTRAINT:** midToEntry must stay populated BEFORE the next event-loop yield because `ontrack` (from setRemoteDescription) can fire and needs midToEntry to route — so you CANNOT simply defer all midToEntry writes to after the PUT. **Required fix:** make the op transactional-on-failure: record the exact mids added in THIS op (and snapshot the prior subscribedTracks); wrap the post-SRD section so that if anything after the early-populate fails (esp. the renegotiate PUT), you ROLL BACK — delete the this-op mids from `this.midToEntry`, restore `this.subscribedTracks` to the prior snapshot, attempt `rollbackPendingLocalOffer()` (PC rollback) — then rethrow so the retry path starts from a clean, consistent state. The no-renegotiation else-branch (~1494) must be equally consistent. Net invariant: after doSubscribeTracks returns OR throws, `this.midToEntry` and `this.subscribedTracks` agree (no orphaned mids).
- **SFU-S2 (MED) — new cfSessionId, same clientId.** `handleSfuPresence` (~line 864) / `handleSfuRoster` (~886): when `prev.cfSessionId !== msg.cfSessionId` (publisher reconnected with a NEW CF session) the code resets retry state (~867) but does NOT evict that clientId's STALE subscribed entries (old mids in midToEntry/subscribedTracks). So the fresh subscribe can collide with stale mids for that clientId. Fix: on detecting a new cfSessionId for a known clientId, evict that clientId's prior subscribed entries (the existing per-clientId removal path — see the midToEntry.delete loops ~905/947/990) BEFORE the fresh subscribe, so the new session subscribes cleanly. Reuse the existing eviction helper; don't invent a new one.
- **SFU-S3 (MED) — reconcile positional + kind-only.** `frontend/src/app/services/sfu-mid-reconcile.ts` `reconcileSubscribedMids(...)`: matches responseTracks[i] ↔ newTransceiverMids[i] positionally then validates receiver-kind. CF returns mid:"" for remote tracks so positional is the only signal; kind validation disambiguates audio vs video but CANNOT catch a swap between two SAME-kind tracks from one publisher. Fix (deterministic-only — do NOT over-engineer): strengthen the guard where it can be made stronger — e.g. assert per-kind COUNT parity (number of response tracks of each kind == number of NEW transceivers of that kind) and trackName uniqueness, so a count/kind drift fails loudly into the retry path; keep positional WITHIN a kind (best available given CF's mid:""). Document the residual single-publisher-2-same-kind limitation honestly. ALSO fix the stale spec (TS2): the reconcileSubscribedMids spec/caller arg count must match the current 5-param signature (responseTracks, newTransceiverMids, transceivers, trackKindMap, publisherClientId).
- **SFU-S4 (MED) — screen-publish rollback gap.** `doPublishScreen()` (~line 1127): on a partway failure (addTransceiver ~1137 → setLocalDescription ~1139 → POST /api/sfu/tracks ~1157 → setRemoteDescription), there is no rollback, leaving an added transceiver / `this.screenSender` set and a dangling local offer. Fix: mirror the main-publish rollback — on failure, `rollbackPendingLocalOffer()`, remove/stop the added screen transceiver/sender, clear `this.screenSender`, and rethrow. So a failed screen publish leaves the PC + state clean (no orphan sender, screen can be retried).
