## Contributing bugs / races / alternative causes (each with file:line)
- `subscribedClientIds` is set before enqueue in `subscribeIfNeeded()`, then cleared on fail/retry; this blocks duplicate concurrent subscribe for one publisher but can also mask cross-publisher timing races where only the later subscription path performs successful on-track attachment. `subscribeIfNeeded` and retry clear path: frontend/src/app/services/sfu-client.service.ts:150-170, 159-163, 1639-1670. 
- `midToEntry` is also updated in `remote-track` reconcile and never snapshot-verified against all currently subscribed publisher mids after renegotiation/renumbering; stale mappings can stay alive while later mappings replace ownership. frontend/src/app/services/sfu-client.service.ts:1683-1700, 1715-1730.
- Track name / kind mapping is only from advertised/response pairs and strict size checks; if Cloudflare returns differing same-kind ordering, reconcile throws and drops new subscribe attempts, which can cause one active audio source only. frontend/src/app/services/sfu-mid-reconcile.ts:1-140.
- Kickstart elements are created per source but explicitly muted (`audio.muted = true`), so they never provide audibility by themselves and can hide decode issues until mixer output is proven. frontend/src/app/services/remote-audio.service.ts:552-557.
- If sink id application fails silently (fallback to default), UI only knows blocked state; no explicit per-element sink id success/error capture exists in diagnostics payload. frontend/src/app/services/remote-audio.service.ts:652-657, frontend/src/app/pages/room/room.page.ts:690-696.

## Fix approach (mechanism-level, file:line — what to change and why it closes the goal)
1. Make host playout deterministically gated on a valid gesture + playing output and capture that state in banner/recovery loops: in `room.page.ts:631-681` keep `remoteAudioBlocked` as it already keys off `contextState === 'running' && outputPlaying`, but remove any non-gesture recovery path that can be reached without user action and ensure `unlockAudioFromGesture` is only used from explicit user interactions (`enableRemoteAudio`, tile/audio user actions). This prevents “running state never resumed” for both sources and directly addresses A.
2. Harden host playout fallback by also validating mixer output element `srcObject` and `readyState` in `RemoteAudioService` before declaring playable, and keep recovery counters from attempting silent play when no sink is configured. Update `remote-audio.service.ts:538-542, 660` + `room.page.ts:650-660`. This makes A fail-fast and recoverable instead of hidden silence.
3. Close B at the subscriber-map layer: in `sfu-client.service.ts:1609-1766`, add post-`reconcileSubscribedMids` validation that replays/keeps prior `midToEntry` for already-active publisher mids and refuses to overwrite an existing mapped mid without explicit teardown of that specific old mapping. Also when remapping mids, emit transition logs keyed by `publisherClientId + mid` so we can prove whether A is displaced by B mid reuse. This directly targets one-at-a-time remap behavior.
4. Add a diagnostic invariant in the same subscribe path: after successful `doSubscribeTracks`, assert that every publisher with `advertised audio tracks` still has a non-empty `remoteStreams` entry and emit a one-shot warning when any previously subscribed publisher disappears while still announced as live. Add in `sfu-client.service.ts:804-827` / `doSubscribeTracks`.
5. Keep mixer capable of handling both sources by ensuring `syncPeers()` never deletes by stale stream churn and by avoiding forced stream replacement from unrelated track replacement events. Current behavior in `remote-audio.service.ts:243-258` is structurally okay for multi-source; confirm with tests before touching.
