## Contributing bugs / races / alternative causes (each with file:line)
- `remoteAudioBlocked` can be true for a running context with paused output, but automatic interaction recovery is installed only when `contextState !== 'running'`; a running context plus blocked/paused mixer output may rely on the visible button only. Evidence: frontend/src/app/pages/room/room.page.ts:650, frontend/src/app/pages/room/room.page.ts:658, frontend/src/app/pages/room/room.page.ts:659, frontend/src/app/pages/room/room.page.ts:674.
- `bindOutputElement()` binds `destination.stream` and unmutes but does not call/play within a gesture. Evidence: frontend/src/app/services/remote-audio.service.ts:538, frontend/src/app/services/remote-audio.service.ts:541, frontend/src/app/services/remote-audio.service.ts:542.
- The kickstart elements are muted, so they may keep WebRTC tracks alive but cannot make audio audible; they are not a fallback audible sink. Evidence: frontend/src/app/services/remote-audio.service.ts:552, frontend/src/app/services/remote-audio.service.ts:557, frontend/src/app/services/remote-audio.service.ts:558.
- Sink selection is a plausible but less likely A contributor: `applyMediaElementSinkWithDefaultFallback` should clear bad selected sinks and fall back to default, so stale sinkId alone is not the current best explanation. Evidence: frontend/src/app/services/remote-audio.service.ts:94, frontend/src/app/services/remote-audio.service.ts:103, frontend/src/app/services/remote-audio.service.ts:106.
- Roster replacement is not the B root by itself: backend presence is keyed by `clientId`, stores multiple entries, and tests cover a late joiner seeing both publishers. Evidence: backend/src/modules/signaling/index.ts:53, backend/src/modules/signaling/index.ts:722, backend/src/modules/signaling/index.ts:1087, backend/tests/signaling-sfu-presence.test.ts:128.
- `currentSubscribedTrackNames()` is globally keyed by trackName, not clientId+trackName. Track names are UUID-bearing in normal publish, so this is probably safe, but if two publishers ever advertised the same trackName it would suppress the second subscription. Evidence: frontend/src/app/services/sfu-client.service.ts:1058, frontend/src/app/services/sfu-client.service.ts:1060, frontend/src/app/services/sfu-client.service.ts:1559.

## Fix approach (mechanism-level, file:line — what to change and why it closes the goal)
- For A: make remote playout activation deterministic after sources/output exist. In `remote-audio.service.ts`, introduce a durable "needs user activation" state when `output.play()` rejects or `outputPlaying` remains false with sources; keep interaction listeners installed for `contextState !== 'running' OR output not playing with sources`, not just suspended context. Relevant code: frontend/src/app/pages/room/room.page.ts:650, frontend/src/app/pages/room/room.page.ts:661, frontend/src/app/pages/room/room.page.ts:674, frontend/src/app/pages/room/room.page.ts:2799.
- For A: on the user activation handler/button, synchronously call `unlockAndPlayRemoteSinks()` while the output element and current mixer sources exist, and only clear `remoteAudioBlocked` after `contextState === 'running' && outputPlaying === true`. Relevant code: frontend/src/app/pages/room/room.page.ts:1049, frontend/src/app/pages/room/room.page.ts:2661, frontend/src/app/services/remote-audio.service.ts:263, frontend/src/app/services/remote-audio.service.ts:294.
- For B: after every subscribe SRD/renegotiate, audit all `midToEntry` entries against live transceivers and inbound stats; if a previously subscribed publisher's receiver is stopped/ended/inactive or its inbound stat disappears while the publisher is still advertised, clear only that publisher's subscription guard and resubscribe. Relevant code: frontend/src/app/services/sfu-client.service.ts:1715, frontend/src/app/services/sfu-client.service.ts:1724, frontend/src/app/services/sfu-client.service.ts:1763, frontend/src/app/services/sfu-client.service.ts:1075.

Existing tests validate single subscribe and roster, but not this exact two-publisher additive receive path. Relevant code: frontend/src/app/services/sfu-client.spec.ts:1413, backend/tests/signaling-sfu-presence.test.ts:128.
