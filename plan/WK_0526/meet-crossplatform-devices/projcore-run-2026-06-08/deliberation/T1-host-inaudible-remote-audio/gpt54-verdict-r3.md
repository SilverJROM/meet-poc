# gpt54 verdict — T1 round 3 (red-team)
## Blockers found in the fix plan (each: what breaks + file:line + how to fix)
- `Volume / mute-all break if the audible mixer is simply retired.` The speaker UI is wired directly to `RemoteAudioService.setMutedAll()` and `setVolume()` at [controls-bar.component.ts:108-121](/home/agjrom/websites/meet-poc/frontend/src/app/components/controls-bar/controls-bar.component.ts:108), but those methods only drive the mixer gain node at [remote-audio.service.ts:195-205](/home/agjrom/websites/meet-poc/frontend/src/app/services/remote-audio.service.ts:195). Per-tile `<audio>` elements in [tile.component.html:14-15](/home/agjrom/websites/meet-poc/frontend/src/app/components/tile/tile.component.html:14) never read `remoteAudio.volume()` or `remoteAudio.mutedAll()`, and `TileComponent` just sets `audio.muted = false` then `play()` at [tile.component.ts:57-63](/home/agjrom/websites/meet-poc/frontend/src/app/components/tile/tile.component.ts:57). If the mixer leaves the audible path without replacing these controls, the “meeting speakers” slider and mute button become dead UI. Fix: keep a minimal remote-audio state service and bind each tile element’s `.volume` / `.muted` from that state, or route tiles through a non-shared per-element Web-Audio stage that preserves control semantics.
- `Feedback-limiter loss is a real regression, not a cosmetic one.` The only feedback suppression in the current playout path is the brick-wall compressor at [remote-audio.service.ts:56-58](/home/agjrom/websites/meet-poc/frontend/src/app/services/remote-audio.service.ts:56) and [remote-audio.service.ts:518-527](/home/agjrom/websites/meet-poc/frontend/src/app/services/remote-audio.service.ts:518). Consensus says retire the mixer from the audible path, but that also removes the limiter. With same-room / open-speaker setups, the app loses an explicit safety mechanism. Fix: either keep a limiter in a new per-element audible graph, or explicitly accept this regression and prove browser/OS AEC is sufficient. Right now the plan does neither.
- `Naive mid-overwrite throw can itself violate the no-suppress directive.` The agreed B guard is to refuse cross-publisher overwrite near [sfu-client.service.ts:1751-1754](/home/agjrom/websites/meet-poc/frontend/src/app/services/sfu-client.service.ts:1751). But mid-call subscribe errors feed the capped retry path at [sfu-client.service.ts:1100-1133](/home/agjrom/websites/meet-poc/frontend/src/app/services/sfu-client.service.ts:1100), and once capped the client logs “permanently stopped” and gives up. If Cloudflare legitimately reuses a `mid` after the old owner is stale, a pure throw-only guard can strand the new publisher unsubscribed after 7 attempts, which is exactly a suppressed voice. Fix: make the guard reclaim-safe: allow overwrite only after proving the old owner is gone/stale and closing or clearing that owner’s mapping first; only throw on true live cross-publisher conflict.
- `Do not delete RemoteAudioService wholesale.` Consensus hints it might be deletable after switching to per-tile audio. That is unsafe because `unlockAudioFromGesture()` depends on `remoteAudio.unlockAndPlayRemoteSinks()` at [room.page.ts:2661-2668](/home/agjrom/websites/meet-poc/frontend/src/app/pages/room/room.page.ts:2661), the speaker controls depend on its state at [controls-bar.component.ts:35](/home/agjrom/websites/meet-poc/frontend/src/app/components/controls-bar/controls-bar.component.ts:35), and `handleRemoteAudioBlocked()` / `enableRemoteAudio()` rely on that banner flow at [room.page.ts:1045-1050](/home/agjrom/websites/meet-poc/frontend/src/app/pages/room/room.page.ts:1045). Fix: keep a slimmed service for per-element unlock, sink routing helpers, and speaker state even if the audible mixer graph is retired.

## Regressions the fix would introduce (volume/mute-all/feedback-limiter/sink/autoplay) + mitigation
- `Volume regression`: direct tile audio currently ignores `remoteAudio.volume()`. Mitigation: in `TileComponent`, bind `audio.volume = remoteAudio.volume()` reactively, and preserve `MAX_VOLUME` semantics or redefine them if HTMLMediaElement volume caps at `1.0`.
- `Mute-all regression`: direct tile audio currently forces `audio.muted = false` at [tile.component.ts:61](/home/agjrom/websites/meet-poc/frontend/src/app/components/tile/tile.component.ts:61). Mitigation: gate that off `remoteAudio.mutedAll()` instead of hardcoding `false`.
- `Feedback-limiter regression`: retiring the audible mixer removes [FEEDBACK_LIMITER_PARAMS](/home/agjrom/websites/meet-poc/frontend/src/app/services/remote-audio.service.ts:58). Mitigation: either keep a limiter in a new per-element graph or keep the mixer as an optional post-fader safety stage but never as the sole playout route.
- `Selected-output race on new tiles`: `TileComponent` calls `audio.play()` immediately after `srcObject` attach at [tile.component.ts:60-63](/home/agjrom/websites/meet-poc/frontend/src/app/components/tile/tile.component.ts:60), but it never sets `sinkId` itself. The selected device is applied later by the room effect that watches `selectedAudioOutputId()` and `peers()` then calls `applySpeakerDevice()` via `setTimeout` at [room.page.ts:686-690](/home/agjrom/websites/meet-poc/frontend/src/app/pages/room/room.page.ts:686). `applySpeakerDevice()` does select all `video, audio` elements at [room.page.ts:2648-2658](/home/agjrom/websites/meet-poc/frontend/src/app/pages/room/room.page.ts:2648), so eventually the tile reaches the selected device, but there is a first-frame race where the tile can start on the system default device before rerouting. Mitigation: set `sinkId` in the tile before `play()`, or pass selected output id into the tile and call the shared sink helper there.
- `Autoplay recovery hole if mixer-specific recovery is removed without replacement`: per-tile autoplay rejection does emit `remoteAudioBlocked` at [tile.component.ts:63-65](/home/agjrom/websites/meet-poc/frontend/src/app/components/tile/tile.component.ts:63), and the banner handler sets the signal at [room.page.ts:1045-1046](/home/agjrom/websites/meet-poc/frontend/src/app/pages/room/room.page.ts:1045). The banner button then calls `unlockAudioFromGesture()` which already queries `audio[data-remote-audio]` elements in `unlockAndPlayRemoteSinks()` [remote-audio.service.ts:282-292](/home/agjrom/websites/meet-poc/frontend/src/app/services/remote-audio.service.ts:282). That part is sound. The regression risk is if implementation removes the mixer service and also deletes this generic query-selector-based unlock path. Mitigation: keep the per-element unlock loop even if the mixer graph is removed.

## New issue / 7th mechanism (or "NONE — fix plan sound")
- `7th issue: duplicate DOM tracking key can still collapse concurrent remote tiles/audio elements.` The room renders peers with `@for (peer of orderedStripPeers(); track peer.participantId)` at [room.page.html:272](/home/agjrom/websites/meet-poc/frontend/src/app/pages/room/room.page.html:272) and `@for (peer of peers(); track peer.participantId)` at [room.page.html:286](/home/agjrom/websites/meet-poc/frontend/src/app/pages/room/room.page.html:286). If two live remote clients share a `participantId` (same person on multiple devices, exactly the class of scenario under audit), Angular may reuse/collapse the tile DOM, which means one remote `<audio>` element can be lost even after re-enabling per-tile audio. This is independent of the SFU subscribe logic and directly threatens the “all concurrent publishers audible” directive. Fix: track by `peer.id` / `clientId`, not `participantId`.
- `Diagnostics privacy footgun`: adding raw selected output-device IDs to diagnostics will log another stable device identifier, similar to existing selected input IDs at [room.page.ts:3509-3510](/home/agjrom/websites/meet-poc/frontend/src/app/pages/room/room.page.ts:3509). Not a blocker, but if diagnostics leave the host machine, hash or redact before persistence.
