## False-positive banner risk (silent participant)

Real. Current code assumes "genuinely silent speaker: bytes are not climbing" (covered only by a bytes-flat unit fixture), but the production predicate has no silence classifier. `remoteVoiceBytesClimbed()` is a raw `last.bytes > first.bytes` check (frontend/src/app/pages/room/room.page.ts:3891-3893), `decideVoiceRecovery()` accepts any positive byte delta with flat emitted count (frontend/src/app/services/remote-audio.service.ts:74-82), and the resulting latch only clears on emitted advancement (frontend/src/app/pages/room/room.page.ts:2747-2750; frontend/src/app/services/remote-audio.service.ts:261-263). Therefore a quiet remote that produces RTP/CN/keepalive bytes without emitted audio advancement can trip the banner even though no speech should be heard; once tripped, continued silence provides no clear signal.
