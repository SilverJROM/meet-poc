# codex55 verdict — T1 round 2
## Q1 — A-mechanism ranking (with the discriminator evidence file:line)
1. **A4 sink/output routing on the single mixer element — most likely.** It best matches all new host facts: no banner, silence, specific output selected, other apps/Meet audible. Our only audible remote path is one `<audio #remoteAudioMixer>` (frontend/src/app/pages/room/room.page.html:229), fed by a Web-Audio `MediaStreamAudioDestinationNode.stream` (frontend/src/app/services/remote-audio.service.ts:528, frontend/src/app/services/remote-audio.service.ts:541), then routed through `setSinkId` using the selected device (frontend/src/app/pages/room/room.page.ts:2667, frontend/src/app/services/remote-audio.service.ts:652). If that element reports playing/running while the selected sink does not emit this Web-Audio-derived stream, the banner stays clear because the banner only checks context running + `outputPlaying` (frontend/src/app/pages/room/room.page.ts:650, frontend/src/app/pages/room/room.page.ts:658). Code cannot prove Chrome honors `setSinkId` differently for this stream; it only proves we rely on one routed mixer element.
2. **A3 orphaned graph after closed AudioContext — very likely and code-proven.** `ensureGraph()` creates a new `AudioContext` when the old one is closed, but it does not null/recreate `gain`, `limiter`, or `destination` in that branch (frontend/src/app/services/remote-audio.service.ts:507, frontend/src/app/services/remote-audio.service.ts:514, frontend/src/app/services/remote-audio.service.ts:518, frontend/src/app/services/remote-audio.service.ts:528). `addSource()` then creates a source in the new context and connects it to the stale `gain`; a cross-context/closed-node connect can throw, the catch only logs, and `sources.set()` is skipped (frontend/src/app/services/remote-audio.service.ts:464, frontend/src/app/services/remote-audio.service.ts:468, frontend/src/app/services/remote-audio.service.ts:472, frontend/src/app/services/remote-audio.service.ts:475). With `sources.size === 0`, the no-banner fact is explained because the banner returns early when `hasSources` is false (frontend/src/app/pages/room/room.page.ts:654, frontend/src/app/pages/room/room.page.ts:657).
3. **A5 single shared mixer SPOF — proven architectural amplifier.** Per-tile audio is disabled whenever the mixer is enabled (frontend/src/app/pages/room/room.page.html:253, frontend/src/app/pages/room/room.page.html:293), kickstart elements are explicitly muted (frontend/src/app/services/remote-audio.service.ts:552, frontend/src/app/services/remote-audio.service.ts:557), and every remote source is funneled to one destination/output element (frontend/src/app/services/remote-audio.service.ts:467, frontend/src/app/services/remote-audio.service.ts:531, frontend/src/app/services/remote-audio.service.ts:541). This makes either A3 or A4 all-participant silent.
4. **A1 gesture/source guard — real but less complete.** The join gesture calls unlock before remote sources may exist (frontend/src/app/pages/room/room.page.ts:853), and `unlockAndPlayRemoteSinks()` only plays the mixer output when `sources.size > 0` (frontend/src/app/services/remote-audio.service.ts:294). Later sync/recovery play attempts are scheduled outside the gesture (frontend/src/app/pages/room/room.page.ts:637, frontend/src/app/services/remote-audio.service.ts:594). This explains blocked output, but if sources existed and output was not playing the banner should appear (frontend/src/app/pages/room/room.page.ts:650).
5. **A2 pure autoplay-suspended context — demoted.** A suspended context with sources should surface the banner because playability requires `contextState === 'running'` when sources exist (frontend/src/app/services/remote-audio-playability.ts:113, frontend/src/app/services/remote-audio-playability.ts:114), and the room effect sets `remoteAudioBlocked` when sources exist and running/outputPlaying is false (frontend/src/app/pages/room/room.page.ts:654, frontend/src/app/pages/room/room.page.ts:658). JROM saw no banner, so A2 alone does not fit.
6. **A6 zero-gain keepalive auto-suspend — lowest.** The keepalive oscillator is routed through gain 0 (frontend/src/app/services/remote-audio.service.ts:621, frontend/src/app/services/remote-audio.service.ts:624), but any resulting suspended-with-sources state should still trip the same banner path. It is a hardening item, not the best root.

## Q2 — Anomaly B verdict: SEQUENTIAL (B2 primary) — proof file:line
**Verdict: SEQUENTIAL as the evidence-based primary; B1 is a real guardrail bug but not proven as the observed cause.**

Code can keep two concurrent publishers in the normal subscribe path. Publisher 2 subscription snapshots existing mids, reconciles only new transceiver mids, and initializes `nextSubscribed` from the prior subscribed map, so publisher 1 entries survive (frontend/src/app/services/sfu-client.service.ts:1639, frontend/src/app/services/sfu-client.service.ts:1673, frontend/src/app/services/sfu-client.service.ts:1720, frontend/src/app/services/sfu-client.service.ts:1724, frontend/src/app/services/sfu-client.service.ts:1728, frontend/src/app/services/sfu-client.service.ts:1763). `processOntrack()` is additive by `publisherClientId`; it gets or creates one `MediaStream` per publisher and adds the track without deleting other publishers (frontend/src/app/services/sfu-client.service.ts:804, frontend/src/app/services/sfu-client.service.ts:820, frontend/src/app/services/sfu-client.service.ts:826). The room peer list also reads `remoteStreams` by client ID, not by a single active speaker (frontend/src/app/pages/room/room.page.ts:327, frontend/src/app/pages/room/room.page.ts:331). The mixer then keys sources by peer ID and can hold multiple IDs (frontend/src/app/services/remote-audio.service.ts:243, frontend/src/app/services/remote-audio.service.ts:247, frontend/src/app/services/remote-audio.service.ts:253).

The observed host timeline has an explicit no-inbound gap between Windows and phone: peer2 audio runs through 00:26:45, then 00:26:52 has no inbound audio, then Phone Peer2 starts at 00:27:00 (plan/WK_0526/meet-crossplatform-devices/projcore-run-2026-06-08/diagnostics-evidence-2026-06-08.md:26, plan/WK_0526/meet-crossplatform-devices/projcore-run-2026-06-08/diagnostics-evidence-2026-06-08.md:27, plan/WK_0526/meet-crossplatform-devices/projcore-run-2026-06-08/diagnostics-evidence-2026-06-08.md:28). That fits one publisher stopping/leaving before the other becomes active better than code-mandated displacement.

B1 still needs a fix/test: in the no-renegotiation branch, any returned `rt.mid` is blindly written to `midToEntry` and `nextSubscribed`; if Cloudflare returns an already-used mid for another publisher, this overwrites attribution/routing state (frontend/src/app/services/sfu-client.service.ts:1747, frontend/src/app/services/sfu-client.service.ts:1751, frontend/src/app/services/sfu-client.service.ts:1753, frontend/src/app/services/sfu-client.service.ts:1754). Existing tests cover single subscribe and preserving old mids during one-publisher new-track subscribe, but do not prove publisher A + publisher B concurrent audio (frontend/src/app/services/sfu-client.spec.ts:1413, frontend/src/app/services/sfu-client.spec.ts:1435, frontend/src/app/services/sfu-client.spec.ts:1443).

## Q3 — Fix set: per-publisher-elements + concrete change list (file:line) + R3 diag fields
**Choose `per-publisher-elements`.** The host evidence points at output/sink delivery, and the single Web-Audio mixer is the common failure point. Meet-style unmuted per-publisher `<audio>` elements with each remote stream as `srcObject` dissolve A1/A3/A4/A5 for live playout: no Web-Audio graph required for audibility, no single `MediaStreamAudioDestinationNode` sink, no sources-size guard before output play, and one bad element cannot silence everyone.

Concrete change list I would commit:
- `frontend/src/app/services/remote-audio.service.ts`: make live playout per-publisher. Replace/augment `RemoteSource` so each remote peer owns an **unmuted** `HTMLAudioElement` with `data-remote-audio`, `autoplay`, `playsinline`, `srcObject = stream`, selected `sinkId`, and `play()` attempted on source add and on user gesture. Current muted kickstart code is at frontend/src/app/services/remote-audio.service.ts:552 and must not remain the only per-peer element.
- `frontend/src/app/services/remote-audio.service.ts`: keep Web-Audio mixer only as optional analysis/limiter fallback or remove it from the audible path. If any graph remains, fix A3 by recreating `gain`, `limiter`, `destination`, and keepalive whenever a new context is created after `closed` (frontend/src/app/services/remote-audio.service.ts:507, frontend/src/app/services/remote-audio.service.ts:514, frontend/src/app/services/remote-audio.service.ts:528).
