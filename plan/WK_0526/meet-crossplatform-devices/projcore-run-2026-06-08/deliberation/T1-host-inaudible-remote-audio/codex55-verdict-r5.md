# codex55 verdict — T1 round 5
## Q1 — Ownership: service-owned vs tile-registered — pick + why (file:line)
**Pick service-owned elements.** The central registry should create/own hidden `<audio data-remote-audio>` elements under `RemoteAudioService`, keyed by `publisherClientId` / `peer.id`.

Why this is correct in this app:
- The current tile path is visually duplicated in share mode: the same peer can render in share-stage and strip (frontend/src/app/pages/room/room.page.html:249, frontend/src/app/pages/room/room.page.html:272), while `orderedStripPeers()` returns all peers (frontend/src/app/pages/room/room.page.ts:444). Tile-owned audio has to solve duplicate ownership; service-owned audio avoids it by construction.
- The canonical remote key is already `clientId` / `peer.id`, not participantId: `peers()` iterates `peerIdentities` by clientId and assigns `id: clientId` (frontend/src/app/pages/room/room.page.ts:299, frontend/src/app/pages/room/room.page.ts:329, frontend/src/app/pages/room/room.page.ts:333). SFU streams are keyed by `publisherClientId` in `remoteStreams` (frontend/src/app/services/sfu-client.service.ts:820, frontend/src/app/services/sfu-client.service.ts:826). This matches the registry key and avoids same-person/two-device collisions.
- Service ownership keeps sink, volume, mute, unlock, recovery, and cleanup in one owner. Those controls already route through RemoteAudioService and room recovery (frontend/src/app/components/controls-bar/controls-bar.component.ts:35, frontend/src/app/components/controls-bar/controls-bar.component.ts:108, frontend/src/app/components/controls-bar/controls-bar.component.ts:119, frontend/src/app/pages/room/room.page.ts:2667, frontend/src/app/pages/room/room.page.ts:2686, frontend/src/app/pages/room/room.page.ts:2796).
- Service-created elements still get caught by broad speaker routing if appended to `document.body`: `applySpeakerDevice()` queries `document.querySelectorAll('video, audio')` (frontend/src/app/pages/room/room.page.ts:2647, frontend/src/app/pages/room/room.page.ts:2648). But the registry must not rely on that later effect; it should apply the selected sink in `addPublisher`.
- Teardown is already centralized through `cleanupCall()` calling `remoteAudio.reset()` (frontend/src/app/pages/room/room.page.ts:2452, frontend/src/app/pages/room/room.page.ts:2507). `reset()` must be extended to pause/null/remove every registry element, mirroring current source cleanup (frontend/src/app/services/remote-audio.service.ts:444, frontend/src/app/services/remote-audio.service.ts:456).

Angular pitfall: service-created DOM is outside Angular view, so no template lifecycle cleans it up. That is acceptable only if `removePublisher()` and `reset()` own removal. It is better than tile registration because tile lifecycle cannot naturally enforce one audible element across multiple visual instances.

## Q2 — B12 join-order table: (a)(b)(c)(d)(e) each = HEARD / NEEDS-CLICK(banner?) / SILENT-NO-BANNER(gap)
| Case | Verdict | Why |
|---|---|---|
| (a) publisher A subscribes before host's first gesture | **NEEDS-CLICK (banner)** | `addPublisher(A)` applies sink/volume/mute then attempts `play()`. If autoplay rejects before a gesture, registry marks blocked and leaves element registered. Room already has a visible unblock affordance (frontend/src/app/pages/room/room.page.html:221, frontend/src/app/pages/room/room.page.html:225), and the button calls `unlockAudioFromGesture()` (frontend/src/app/pages/room/room.page.ts:1049, frontend/src/app/pages/room/room.page.ts:2661), which must call registry `unlockAll()`. Not silent-no-banner if B8 uses registry blocked state instead of mixer sources. |
| (b) B joins after host gestured once | **HEARD** | `unlockAll()` sets sticky `unlocked=true`; later `addPublisher(B)` applies selected sink and `play()`. This depends on the registry replacing the current mixer unlock path, which currently only loops existing DOM `audio[data-remote-audio]` (frontend/src/app/services/remote-audio.service.ts:282, frontend/src/app/services/remote-audio.service.ts:287). With sticky registry state, no fresh click required. |
| (c) both join before any gesture | **NEEDS-CLICK (banner), then HEARD both** | Both registry elements remain registered after rejected play; one gesture replays all registered elements. Current global interaction recovery is already wired for pointer/click/key (frontend/src/app/pages/room/room.page.ts:2801, frontend/src/app/pages/room/room.page.ts:2802, frontend/src/app/pages/room/room.page.ts:2803), but it must remain installed until registry reports no blocked elements. |
| (d) host gestures, A joins, host never clicks again, B joins much later | **HEARD** | This is the core B12 fix: sticky `unlocked=true` means late `addPublisher()` calls `play()` without requiring another gesture. If browser policy still rejects, registry must set blocked/banner, but the intended design should hear B. Current code lacks sticky state; consensus registry adds it. |
| (e) host backgrounds/resumes then C joins | **HEARD if resume recovery calls registry; otherwise NEEDS-CLICK (banner)** | Visibility recovery currently calls `recoverRemoteAudio('visibility')` when visible (frontend/src/app/pages/room/room.page.ts:2876, frontend/src/app/pages/room/room.page.ts:2879), and pageshow resume also calls recovery (frontend/src/app/pages/room/room.page.ts:2852, frontend/src/app/pages/room/room.page.ts:2856). Registry `recoverPlayback()` must reapply sink and play all existing elements; sticky `unlocked` should let C play when added after resume. If a mobile/browser clears activation after background, the registry must mark blocked and show banner, not silently fail. |

No join order has permanent silent-no-banner **provided** B8 is implemented as registry-authoritative blocked state. If room keeps the current mixer-gated banner (`hasSources` from mixer), cases (a)/(c)/(e) can regress to silent-no-banner because the mixer can be empty (frontend/src/app/pages/room/room.page.ts:654, frontend/src/app/pages/room/room.page.ts:657).

## Q3 — B4 dedup-by-construction holds? (or path that breaks it, file:line)
**Holds if the service owns elements and keys strictly by `peer.id` / publisher client ID.**

The registry map `Map<publisherClientId, ...>` prevents share-stage + strip duplication because visual tile count no longer determines audible element count. The duplicate visual path exists today (frontend/src/app/pages/room/room.page.html:249, frontend/src/app/pages/room/room.page.html:273), but neither tile creates the registry element if service owns playout; room `syncPeers(this.peers())` or an equivalent publisher-stream effect should call `addPublisher(peer.id, peer.stream)` once.

Potential break paths and required guards:
- **participantId key collision:** do not key by `participantId`. The app allows two devices for "peer2"; client IDs differ and publisher ID prefixes differ in evidence. Room peers use `id: clientId` (frontend/src/app/pages/room/room.page.ts:333), so use that.
- **screen+camera same publisher:** screen streams live in `remoteScreenStreams`, but audio remains in the normal `remoteStreams` keyed by clientId (frontend/src/app/pages/room/room.page.ts:327, frontend/src/app/pages/room/room.page.ts:328, frontend/src/app/pages/room/room.page.ts:343). Registry should only consider normal audio tracks, not screen tracks.
- **rejoin race:** `peer-resumed` removes old client ID before adding new identity (frontend/src/app/pages/room/room.page.ts:1909, frontend/src/app/pages/room/room.page.ts:1917, frontend/src/app/pages/room/room.page.ts:1919), and `sfuClient.removePeer()` deletes old `remoteStreams` (frontend/src/app/services/sfu-client.service.ts:968, frontend/src/app/services/sfu-client.service.ts:990). Registry sync must remove old IDs absent from `peers()` before adding new, like existing mixer sync does with `nextIds` (frontend/src/app/services/remote-audio.service.ts:243, frontend/src/app/services/remote-audio.service.ts:247, frontend/src/app/services/remote-audio.service.ts:249).
- **same peer stream replacement:** if a peer's `MediaStream` object changes, `addPublisher` must update `srcObject` rather than create a second element. Current mixer checks stream/track identity (frontend/src/app/services/remote-audio.service.ts:253, frontend/src/app/services/remote-audio.service.ts:255); registry needs the same guard.

## Q4 — 13th issue (or "NO NEW ISSUE — registry design complete")
**13th issue found: R3 diagnostics design still has no concrete type/payload owner for registry playout state.**

Consensus says diagnostics should include per-element `{paused, muted, sinkId, srcObjectAttached}`, but current diagnostics types only include SFU transport/inbound stats and selected capture device IDs (frontend/src/app/services/meeting-sessions.service.ts:276, frontend/src/app/services/meeting-sessions.service.ts:324, frontend/src/app/services/meeting-sessions.service.ts:345, frontend/src/app/services/meeting-sessions.service.ts:356). `buildDiagnosticsPayload()` currently writes selected mic/camera IDs, not selected audio output ID or remote playout registry state (frontend/src/app/pages/room/room.page.ts:3498, frontend/src/app/pages/room/room.page.ts:3509, frontend/src/app/pages/room/room.page.ts:3525). Without adding a first-class `remoteAudioPlayout` payload shape sourced from `RemoteAudioService.debugSnapshot()`, the next call can still fail without proving whether registry elements were paused, muted, sink-routed, or attached.

Required fix: add a diagnostics type like `RemoteAudioPlayoutDiagnostics` to `meeting-sessions.service.ts`, include selected audio output ID, `unlocked`, `blockedPeerIds`, and per-publisher `{publisherClientId, trackId, paused, muted, volume, sinkId, srcObjectAttached, readyState}`; populate it in `room.page.ts` alongside `sfuDiagnostics`; render it on diagnostics page. Device IDs should be redacted or labeled default/selected if privacy is a concern.
