# codex55 CODE red-team CR9 (lens L9: privacy/perf/closure)

## Privacy/security of payload: leak

Owner-only read gating is present for diagnostics: list/detail/download all require auth and query by owner email (`backend/src/modules/sessions/index.ts:115`, `backend/src/modules/sessions/index.ts:129`, `backend/src/modules/sessions/index.ts:143`; store owner filter at `backend/src/modules/sessions/store.ts:397`, `backend/src/modules/sessions/store.ts:414`, `backend/src/modules/sessions/store.ts:473`). Guest/non-owner diagnostics upload is intentionally admitted-client gated by `clientId`/`participantId`/`clientKey` (`backend/src/modules/sessions/index.ts:155`, `backend/src/modules/sessions/index.ts:159`; `backend/src/modules/signaling/index.ts:507`).

Device ids and endpoint IPs are not redacted in the stored/downloaded JSON payload. The client sends raw `selectedAudioDeviceId`, `selectedAudioOutputId`, and `selectedVideoDeviceId` (`frontend/src/app/pages/room/room.page.ts:3535`, `frontend/src/app/pages/room/room.page.ts:3536`, `frontend/src/app/pages/room/room.page.ts:3537`), raw per-publisher `sinkId` and `trackId` (`frontend/src/app/services/remote-audio.service.ts:410`, `frontend/src/app/services/remote-audio.service.ts:414`), and raw SFU candidate addresses/ports (`frontend/src/app/services/sfu-client.service.ts:784`, `frontend/src/app/services/sfu-client.service.ts:787`). The diagnostics UI redacts sink labels for display (`frontend/src/app/pages/diagnostics/diagnostics.page.ts:100`), but the backend persists the raw payload (`backend/src/modules/sessions/store.ts:282`) and the JSON download returns it (`backend/src/modules/sessions/index.ts:143`).

The above raw device/IP fields are owner-only gated, so I do not see a non-owner participant reading another participant's IP/device ids through the diagnostics API. In the current SFU path, the selected candidate pair is local-to-SFU, not peer-to-peer, so it should not expose another participant's residential IP. The advertised publisher manifest exposes `clientId`, `participantId`, display name fallback, and SFU `trackName`s (`frontend/src/app/pages/room/room.page.ts:3561`, `frontend/src/app/pages/room/room.page.ts:3568`, `frontend/src/app/pages/room/room.page.ts:3569`, `frontend/src/app/pages/room/room.page.ts:3571`). That is owner-only call metadata and not cross-tenant visible.

**New security bug:** diagnostics persist and expose raw `clientKey`. The room page includes `clientKey: readClientKey()` in every diagnostics payload (`frontend/src/app/pages/room/room.page.ts:3530`), the backend stores the whole payload (`backend/src/modules/sessions/store.ts:282`) and also stores `participant_client_key` (`backend/src/modules/sessions/store.ts:288`). Signaling treats `clientKey` as the durable "unforgeable, post-admission-only anchor" for diagnostics/reconnect identity (`backend/src/modules/signaling/index.ts:523`) and uses it to match admitted/reconnecting posters (`backend/src/modules/signaling/index.ts:495`, `backend/src/modules/signaling/index.ts:507`). This credential should be used to authorize the POST, then stripped or hashed before persistence/readback.

Payload size is bounded enough for the 5-10 publisher target: Express JSON body limit is 1 MB (`backend/src/server.ts:33`), retained rows are capped at 720 per session (`backend/src/modules/sessions/store.ts:5`, `backend/src/modules/sessions/store.ts:318`), and publisher/track fields grow linearly with admitted publishers/tracks. There is no per-publisher payload size cap beyond the route body limit.

## Perf-at-scale: OK

For 5-10 publishers I do not see a scale blocker. `syncPeers()` builds current remote-audio peers once, removes stale ids, and adds/replaces changed tracks in linear time over peer count plus registry size (`frontend/src/app/services/remote-audio.service.ts:258`, `frontend/src/app/services/remote-audio.service.ts:267`, `frontend/src/app/services/remote-audio.service.ts:269`, `frontend/src/app/services/remote-audio.service.ts:273`). `playoutDiagnostics()` snapshots registry entries once and maps per publisher (`frontend/src/app/services/remote-audio.service.ts:397`, `frontend/src/app/services/remote-audio.service.ts:405`). `refreshBlockedState()` is an O(n) registry scan (`frontend/src/app/services/remote-audio.service.ts:630`).

`applyOutputDevice()` and replay/recovery use `Promise.all()` over registry entries (`frontend/src/app/services/remote-audio.service.ts:291`, `frontend/src/app/services/remote-audio.service.ts:577`), which is fine for 5-10 publishers. The room-level selected-speaker refresh still does one full DOM scan of non-remote media elements (`frontend/src/app/pages/room/room.page.ts:2648`) plus remote registry routing (`frontend/src/app/pages/room/room.page.ts:2656`) when selected output is reapplied, and an effect depends on `this.peers()` (`frontend/src/app/pages/room/room.page.ts:669`). That can cause extra O(n) sink reapplies during churn, but I do not see O(n^2) steady-state thrash or unbounded timer/element growth at the stated scale.

Element lifecycle looks bounded: one hidden audio element is appended per remote publisher (`frontend/src/app/services/remote-audio.service.ts:454`, `frontend/src/app/services/remote-audio.service.ts:499`) and removed on publisher removal/clear (`frontend/src/app/services/remote-audio.service.ts:544`, `frontend/src/app/services/remote-audio.service.ts:614`, `frontend/src/app/services/remote-audio.service.ts:627`). Keepalive/watchdog timers are singletons (`frontend/src/app/pages/room/room.page.ts:2692`, `frontend/src/app/pages/room/room.page.ts:2724`).

## FINAL closure: does the EXACT JROM scenario now resolve to "host hears both on selected device, honest diagnostics"? any residual original-symptom path?

For the exact JROM mechanism, the functional fix is directionally closed. The old shared Web-Audio mixer path is retired (`frontend/src/app/services/remote-audio.service.ts:236`) and each remote publisher gets its own unmuted direct `<audio>` element with `srcObject = stream`, sink applied before `play()`, and per-element diagnostics (`frontend/src/app/services/remote-audio.service.ts:450`, `frontend/src/app/services/remote-audio.service.ts:459`, `frontend/src/app/services/remote-audio.service.ts:502`, `frontend/src/app/services/remote-audio.service.ts:523`, `frontend/src/app/services/remote-audio.service.ts:397`). This directly addresses the "received clean RTP, non-default selected speaker, no banner, no audible output" failure class by avoiding the single mixed Web-Audio output.

R2 also looks closed in current code: SFU subscription iterates all remote publishers after local publish (`frontend/src/app/pages/room/room.page.ts:683`, `frontend/src/app/pages/room/room.page.ts:687`), stores tracks by `publisherClientId` (`frontend/src/app/services/sfu-client.service.ts:937`, `frontend/src/app/services/sfu-client.service.ts:953`), and inbound diagnostics are keyed by subscribed mid to publisher/track (`frontend/src/app/services/sfu-client.service.ts:843`, `frontend/src/app/services/sfu-client.service.ts:849`). Mid collision handling now fails/retries instead of overwriting a live publisher (`frontend/src/app/services/sfu-client.service.ts:1858`, `frontend/src/app/services/sfu-client.service.ts:1864`, `frontend/src/app/services/sfu-client.service.ts:1876`).

Residual original-symptom path: if `setSinkId(selectedDevice)` succeeds at the browser API level but the selected endpoint produces no audible output, the app cannot prove audibility and may still show no "Tap to enable audio" banner because `play()` can succeed and `remoteAudioBlockingReason()` returns null (`frontend/src/app/services/remote-audio.service.ts:648`). That is no longer the suspected JROM mechanism because direct per-publisher elements match the known-good routing shape, and selected-sink failure/fallback is surfaced (`frontend/src/app/pages/room/room.page.ts:1013`, `frontend/src/app/pages/room/room.page.html:221`). Diagnostics are honest about selected/effective/fallback and per-publisher paused/muted/sink/play state, but they still should not persist raw secrets as noted above.
