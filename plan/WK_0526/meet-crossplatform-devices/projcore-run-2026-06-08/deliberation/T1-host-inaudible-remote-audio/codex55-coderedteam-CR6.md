## Observability

One next-call row can localize many common failures:

- `not-subscribed`: if a known publisher has no `inboundTracks` and no `remoteAudioPlayout.perPublisher` row, suspect subscribe/ontrack failure.
- `decoded-but-not-played`: inbound `bytesReceived`/`totalAudioEnergy` rising while per-publisher element is `paused yes`, `src attached`, or in `blockedPeerIds`.
- `played-to-wrong-sink`: per-publisher `sinkId` differs from `selectedAudioOutputId`, or global `usedFallback`/`effectiveSinkId` reports default fallback.
- `autoplay-blocked`: per-publisher `paused yes` with the publisher in `blockedPeerIds`, plus the visible unblock banner path.
- `muted`: per-publisher `muted yes` / `volume 0` and controls mute-all state.
- `device-unavailable`: selected sink rejection/fallback is visible as `usedFallback: true`, `effectiveSinkId: ''`, and the room speaker-unavailable banner path.

But the answer to the packet's exact question is **NO**, not reliably from one row:

1. **Advertised-but-not-subscribed is ambiguous when the host has no inbound/playout row.** `DiagnosticsPayload.peers` exists in the type but the host emits `peers: []` (`frontend/src/app/services/meeting-sessions.service.ts:406`, `frontend/src/app/pages/room/room.page.ts:3548`), and the row does not include `remotePublishers()` / advertised track names. A row with no inbound and no per-publisher playout cannot distinguish "not subscribed to an advertised sender" from "sender absent/not publishing/not in this row".
2. **Sink timeout and play rejection class are invisible.** `addPublisher()` logs setSinkId timeout but diagnostics only have selected/effective/fallback state (`frontend/src/app/services/remote-audio.service.ts:479-487`, `frontend/src/app/services/remote-audio.service.ts:379-401`). `NotSupportedError`/`AbortError` are stored only in private `playbackFailure`, are treated as non-blocking, and are not emitted (`frontend/src/app/services/remote-audio.service.ts:506-508`, `frontend/src/app/services/remote-audio.service.ts:644-648`). A row can show `paused yes` with no blocked id and no reason.
3. **Actual physical output emission remains unobservable.** If inbound energy and call-wide `media-playout` rise, element is unpaused, `sinkId` equals selected, `usedFallback` is false, and JROM still hears nothing, the row localizes to "browser/OS/device emitted nowhere despite reported selected sink", but it cannot prove whether Chrome routed to the wrong physical device, the selected device was externally silent, or the OS/app mixer suppressed the output. That is an environmental/browser boundary, but it is still one of the requested categories.
