# og-requirements — meet-poc full cutover from mesh WebRTC to Cloudflare Realtime SFU

**Decision (JROM, 2026-05-21):** FULL cutover — every call routes through Cloudflare Realtime SFU; the full-mesh media path is retired. Goal: fix PH↔US lag (CF backbone + nearest-edge routing), enable >5 participants, and do per-receiver video quality (proper "degrade to phones") via simulcast.

**Build cadence (JROM):** Sonnet implementer in tmux (`claude --model sonnet --dangerously-skip-permissions`), codex validates per task, projcore (Opus) oversees + gates. Build starts after JROM field-tests the F1/F2/F3 mesh fixes (same-day) unless JROM says go sooner.

**Credentials:** `SFU_APP_ID`, `SFU_TOKEN` (App Secret) in `.env`. Token is server-side `Authorization: Bearer` ONLY — never sent to the browser. Base URL `https://rtc.live.cloudflare.com/v1/apps/{SFU_APP_ID}`.

**Cloudflare Realtime model (reference):** a Session = one RTCPeerConnection to the nearest CF edge. Tracks are published (`location:"local"`) and subscribed (`location:"remote"` referencing another session's `sessionId`+`trackName`). CF does NO room/presence/admit — our ws signaling stays and additionally carries each participant's CF sessionId + trackNames. Endpoints: `POST /sessions/new`, `POST /sessions/{id}/tracks/new`, **`PUT /sessions/{id}/tracks/update`** (layer prefs / transceiver reuse), `PUT /sessions/{id}/renegotiate`, `PUT /sessions/{id}/tracks/close`, `GET /sessions/{id}`. **There is NO session-close endpoint** — teardown closes tracks + closes the PC; CF reaps the idle session.

## Key design constraints (incorporated from codex plan review, 2026-05-21)

- **Operation queue (load-bearing):** ALL PC-mutating operations (publish, subscribe, close, layer-update, renegotiate) MUST run through a single serialized queue/lock per session. CF may send an offer for subscribe/close while the client is mid-publish → uncoordinated `setLocal/RemoteDescription` collide with `stable`/`have-remote-offer`. Established in B2, used by B4-B7.
- **Track naming:** app-provided `trackName` is globally addressable within the app and must be unique across reconnects/screenshares. Scheme: `{participantId}:{sessionEpoch}:{kind}:{uuid}` (carried in signaling). Never assume `kind` alone is unique.
- **mid persistence:** close/update are **`mid`-based, not trackName-based**. Persist `{publisherClientId, participantId, cfSessionId, trackName, kind, mid, status, revision}` per track. `force:false` close may return a renegotiation SDP; `force:true` stops flow without renegotiation.
- **ICE for client↔CF leg:** use **Cloudflare STUN (`stun.cloudflare.com:3478`)** first + existing TURN as fallback for restrictive networks. Do NOT assume our TURN is "CF ICE."
- **Simulcast fields:** publisher sends RID encodings; subscriber prefs use `preferredRid`, `priorityOrdering`, `ridNotAvailable` (exact field name `ridNotAvailable`). Verify the selected layer via stats/API response — don't assume.
- **CF limits:** 50 API calls/sec/session, 64 tracks/API call, 30s inactive-track GC, operations wait up to 5s for PC `connected`. Affects join storms + reconnect timing.
- **Chat stays on ws** — do NOT move chat to CF DataChannels in this cutover (CF datachannels are unidirectional + separate `/datachannels/*` flow).
- **Roster revision number** to reject stale/out-of-order track announcements (avoid subscribing to withdrawn tracks).
- **`/api/sfu/*` authz:** enforce room membership AND resource ownership — a participant cannot close/update another's tracks or subscribe outside the admitted room.

## Requirements

**SR-0 — Raise/remove the participant cap (early, behind the SFU feature branch).** The signaling server's `MAX_ADMITTED=5` / mobile cap 4 must be raised or removed (with an explicit product cap + CF/billing guard) early enough to prove 3+ and >5 participant calls during the cutover — not deferred to the mesh-teardown batch.

**SR-1 — Backend Cloudflare Realtime proxy module.** A backend module (`backend/src/modules/realtime-sfu/`) that proxies the CF Realtime API server-side using `SFU_APP_ID`/`SFU_TOKEN`: create session, add tracks (local/remote), **update tracks**, renegotiate, close tracks (by mid), get session. The App Secret is injected server-side and NEVER returned to the client. Frontend-facing routes (e.g. `POST /api/sfu/session`, `POST /api/sfu/tracks`, `PUT /api/sfu/tracks/update`, `PUT /api/sfu/renegotiate`, `PUT /api/sfu/tracks/close`) require admitted-membership auth (reuse DR-41) AND resource-ownership checks (can't mutate another participant's tracks / foreign sessions). Config-driven base URL; CF 4xx/5xx error passthrough contract.

**SR-2 — Publish local media to the SFU (single PC).** On joining a call (post-admit), the client creates ONE RTCPeerConnection to CF, adds local audio + a video sender, createOffer → publishes via the backend proxy → setRemoteDescription(answer). Video transceiver is pre-negotiated even when the camera is OFF at join (carry the F2/DR-55 lesson) so enabling the camera later needs no fragile renegotiation. Local mic/cam initial state respected. Observable: a single client joins and the diagnostics show an active CF session with local tracks published.

**SR-3 — Signaling presence: publish each participant's CF session + trackNames.** The ws signaling server (existing) broadcasts, per room, each admitted participant's CF `sessionId` and published `trackNames` (audio / camera-video / screen-video) and updates on track add/remove. Clients maintain a roster of remote publishers. Keep all existing signaling (admit/waiting-room/identity/reconnect/chat/host-controls/media-state); REMOVE only the mesh peer-to-peer SDP/ICE relay (`signal` message) once subscribe works.

**SR-4 — Subscribe to remote tracks + render tiles.** For each remote publisher in the roster, the client subscribes via the backend proxy (`location:"remote"` + their sessionId + trackName), handles the CF renegotiation (CF returns an offer → client answers via the renegotiate endpoint), and renders the remote MediaStream per peer tile via `ontrack`. Audio + video both flow. Late joiners subscribe to everyone already present; new publishers are picked up live.

**SR-5 — Media toggles + screenshare over the SFU.** Mic mute/unmute, camera on/off, and screenshare publish/unpublish work over the SFU (replaceTrack on the local sender / publish a screen track + announce via SR-3 / close on stop). Host controls (mute target, remove, end) still function. No mesh assumptions.

**SR-6 — Simulcast / per-receiver video quality.** Local video is published with multiple simulcast encodings (e.g. high/medium/low). Receivers (or the app, per device) request the appropriate layer so phones get a low layer and desktops a high one WITHOUT degrading the single upload to the worst device. During screenshare, the shared content is prioritized (the "cut camera feeds during a demo" goal becomes layer/track prioritization). This is the proper realization of JROM's "totally degrade video to phones / prioritize the demo."

**SR-7 — Reconnect / leave / teardown over the SFU.** A dropped client transparently reattaches (new CF session announced + old session/tracks invalidated in the roster, retain identity/admit per DR-37/38/39, re-publish + re-subscribe, no ghost tiles — identity dedup/no-ghost reconciliation STAYS since reconnect mints a new CF session + track names). Deliberate Exit closes the client's tracks (by mid) + closes the PC + removes its card immediately (carry the deliberate-exit-vs-drop distinction); the idle CF session is reaped by the 30s GC (no session-close endpoint). Must interact correctly with the DR-37/38/39 reconnect-token semantics and CF's 30s inactivity timeout.

**SR-8 — Retire the mesh media path + mesh-only hardening.** Remove the full-mesh peer-connection management and the strictly mesh-only hardening: per-peer fan-out, **per-peer** glare/perfect-negotiation (BUT keep operation serialization — CF still produces offers), **per-peer** PC-recreate (DR-40 mesh form), per-peer mesh degrade/pause (DR-42 + F3/DR-56 → replaced by SFU simulcast/layer prefs, SR-6), the mesh `signal` relay, DR-31 in its mesh form. **KEEP/ADAPT:** admit/waiting-room/identity/reconnect (DR-37/38/39) + identity dedup/no-ghost, chat (ws), host controls, diagnostics (SR-9), device hot-unplug recovery (DR-46), iOS audio unlock/mixer (DR-45, bind to SFU `ontrack` streams), and **DR-40's single-PC recovery** (ICE-restart/connection-state recovery/media-dead detection/fresh-ICE for the one client↔CF PC — NOT deleted, adapted). ICE = Cloudflare STUN + TURN fallback. No dead code left behind. **(The participant cap MAX_ADMITTED=5/mobile=4 is raised/removed in B0 earlier, not here.)**

**SR-9 — Diagnostics for the SFU topology.** Adapt the DR-54 diagnostics to the SFU shape: one session, publish (outbound-rtp) + subscribe (inbound-rtp per remote track) stats, the CF edge/candidate, audio jitter-buffer, simulcast layer in use. Two-sided server-side logging (DR-41) retained so JROM can still say "I made a call" and projcore pulls forensics.

**SR-10 — Full cutover validation.** End-to-end proof on the real app: 2-party call (camera-off join → camera-on → both see/hear, screenshare visible), 3+ party call (no mesh cap), phone-quality path (low layer), reconnect after a drop, deliberate exit removes the card. Audio + video flow through CF. Diagnostics show the SFU session + per-track stats. Field-validated by JROM on a real PH↔US call (lag expected to drop materially vs the mesh/TURN baseline).
