[lead triage] JROM live-call/theme report triage-only, no app code changed. (1) Controls invisible: CONFIRM theme-contrast hypothesis. ec31720 changed `.controls-bar` to `rgba(255,255,255,.92)` and normal `.control-btn` to `background: var(--panel-bg)` (#fff) with only `--line` (#d8dde6) border, so unselected controls visually disappear on a white bar. Proposed fix: give controls a distinct light-theme surface (`background: var(--panel-soft)` or #f1f4f8), stronger border (#b8c2d0 / `rgba(26,31,43,.18)`), subtle shadow, and selected/hover states that remain blue-tinted; keep off/record/leave semantic colors. (2) No peer video crossing: M-B2/M-B3/M-B5 did not obviously remove `addTrack`; `webrtc.addPeer()` still adds every local track before offer/answer and `ontrack` attaches inbound media. Stronger suspect is signaling race: `room.page.ts` drops `signal` messages when `peers().get(from)` has no PC yet; `admitPeer()` sends `admitted` to the guest and `peer-joined` to host on different sockets, so guest can send an offer before host creates the peer, causing the offer to be discarded and both audio/video never connect. Fix plan: buffer pending ICE/SDP by sender until `addPeer()` creates the PC, then drain; add a regression that forces offer-before-peer-joined ordering. Visibility pause is mobile-gated by `viewport.isMobile()` (`innerWidth <= 1023`), so it should not affect full desktop, but it can pause video in narrow desktop windows/tabs because the gate is viewport width rather than mobile UA; consider changing background pause to `platform.isMobileUA()` or `isMobile && isMobileUA`. (3) Audio/voice: audio uses the same PC/signaling path as video, so the signal race would also break voice. There is no separate audio-specific regression found in `MediaService`; mic track is acquired in lobby, carried into join, and only muted by user/host or local track failure. Validation should assert remote audio track exists and PC reaches connected, not just tile count. (4) Recording: M-B5 mime fallback looks structurally OK; `RecorderService.start()` mixes local + remote audio into a MediaStreamDestination, picks supported webm/mp4/aac, uses no timeslice on iOS, and backend accepts webm/mp4/aac. Main risk is upstream: if P2P race prevents remote streams, recordings will be local-only. Secondary check: because recording creates a new AudioContext on the Record click, the user gesture should satisfy mobile/iOS autoplay policy. Fix-run should include host records after peer connection, downloads/uploads nonzero file, and confirms remote audio present in the mix. (5) Transcript speaker-tagging: feasible, but current mixed recording destroys identity. Minimal design: extend WS/room state to preserve stable participant metadata (`clientId`, displayName, host flag, join/leave times, maybe userEmail hash for authenticated host) and have `RecorderService` accept participant metadata plus an active-speaker timeline from `ActiveSpeakerService` sampled/collapsed around 8Hz. Upload a sidecar JSON next to each recording (or a `recording_metadata` table) with `{sessionId, roomId, recordingStartedAt, participants, segments:[{startMs,endMs,clientId,name,confidence/source}]}` so future transcription can map transcript timestamps to names. Better long-term design: record per-peer audio stems in parallel for accurate attribution/overlap handling; mixed-audio + active-speaker segments is cheaper but cannot reliably attribute overlapping speakers.
